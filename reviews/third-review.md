# Review: third

## Tổng quan

- **Scope**: `D:\projects\third` (NestJS 11, hybrid HTTP :8888 + RMQ listener `third_queue`; runtime Bun/Node). Review `src/` và `scripts/`, bỏ qua `node_modules`, `dist`. Đã đọc CLAUDE.md, API_ENDPOINTS.md, `architech/third-service.architecture.md`.
- **Lưu ý tài liệu**: file architecture mô tả Kafka, nhưng code thực tế dùng RabbitMQ (`src/main.ts:40-51`) nên tài liệu đã lỗi thời.
- **Files đã đọc kỹ**: `main.ts`, `app.module.ts`, `app.controller.ts`, `features/{email,redis,uploads,notification,log,test-scenario}/`*, `packages/{guards,interceptor,filters,pipes,helpers,context,configs,strategy}/*`, `packages/entities/{notification,log,test-scenario}/*`, `database/database.module.ts`, `scripts/recreate-db.ts`, Dockerfile/compose/.env (đã ẩn giá trị).
- **Không có trong service**: webhook (không có endpoint webhook nên không có chữ ký cần verify); transaction DB (chỉ truy vấn đơn lẻ). Tích hợp ngoài gồm Resend, Cloudflare R2 (S3), Redis, và HTTP tới gateway (test-scenario).
- **Đánh giá chung**: logic nghiệp vụ nhỏ và gọn, nhưng **bề mặt bảo mật rất yếu**: upload/delete public, đọc Redis tuỳ ý bằng JWT thường, notification IDOR, secrets bị ghi vào `request_logs`, fallback JWT secret cứng, handler RMQ gần như không validate payload. Hạ tầng dùng auto-ack, Redis không có timeout nên Redis chết sẽ treo toàn bộ HTTP.
- Phương pháp: đọc code tĩnh, không chạy build/test. Mục chưa chắc chắn nằm ở phần "Cần xác minh". Số dòng tính theo từng file (đường dẫn tương đối `src/` trừ khi ghi khác); các dòng ghi dạng `~` là gần đúng.

## Chi tiết (Critical / High)

### TRD-01 (Critical) - Đọc Redis tuỳ ý

```ts
// features/redis/redis.controller.ts
@Get('')
async get(@Query('key') key: string): Promise<string | null> {
  return this.redisService.get(key);
}
// features/redis/redis.rpc.controller.ts
@MessagePattern('redis.get')
get(@Payload() payload: { key: string }) { return this.redisService.get(payload.key); }
```

Không whitelist prefix, không role guard (chỉ `JwtAuthGuard` toàn cục, tức mọi role). CLAUDE.md xác nhận `user` lưu login session và reset-password token qua chính Redis này; API_ENDPOINTS.md mục 16 xác nhận mọi role gọi được `GET /redis`. Kẻ tấn công kích hoạt "forgot password" cho nạn nhân rồi đọc key chứa token (tên key do `user` service đặt, cần xác minh định dạng).

### TRD-02 (Critical) - Upload/Download/Delete public

```ts
@Public() @Delete(':key')
async delete(@Param('key') key: string) { return this.uploadService.delete(key); }
@Public() @Get('download') ...   // key tuỳ ý, không giới hạn prefix `uploads/`
```

`UploadService.delete` xoá bất kỳ key; download đọc bất kỳ object trong bucket. API_ENDPOINTS.md mục 17 ghi "Public" như thiết kế, nhưng vẫn là lỗ hổng thực nếu cổng HTTP bị expose (Dockerfile `EXPOSE 4001`). Nếu chỉ truy cập qua gateway/RMQ thì bề mặt còn lại là RPC `upload.delete`/`upload.download` không kiểm tra quyền sở hữu key.

### TRD-03 (High) - Fallback JWT secret

## Vấn đề tích hợp

1. **Tài liệu Kafka vs RabbitMQ**: `architech/third-service.architecture.md` nói Kafka, `redis.set` là EventPattern fire-and-forget. Thực tế là RMQ và `redis.set` đã là **MessagePattern** request-reply (`redis.rpc.controller.ts:22`). Producer nào còn `emit('redis.set')` sẽ không ghi được (không có handler EventPattern). `redis.del` vẫn là EventPattern: caller dùng `send` sẽ treo tới timeout vì không có reply. Cần rà soát caller ở `user`/`gateway`.
2. `redis.get` **trả** `null`: nếu wrapper `RmqProducer.send()` coi giá trị rỗng/`undefined` là lỗi thì key không tồn tại có thể bị xử lý sai ở `user` (Cần xác minh).
3. **Error payload**: `RpcExceptionFilter` trả `{statusCode, message, errors, serviceName}`; mọi lỗi không phải HttpException thành 500 (gồm `NoSuchKey` của `upload.download`, lỗi UUID, unique violation), lệch bảng lỗi API_ENDPOINTS.md (400/404/409). `ErrorInterceptor` chỉ đăng ký cho HTTP app nên không có tác dụng trên đường RPC (TRD-19).
4. **Notification contract** (API_ENDPOINTS.md mục 14): doc ghi body `{ title, content, type?, receiverId? }` và 400 `"User not found"`; code dùng `userId`, bắt buộc `type`, không kiểm tra user tồn tại; `read-all` doc trả `{ markedAll: true }`, code trả kết quả driver (TRD-20). Schema cho `senderId` trong body nhưng controller luôn ghi đè bằng `user.id`.
5. `GET /redis`: doc cam kết 400 khi thiếu `key`, code không có (TRD-23). `upload.download` qua RPC không trả 404 như doc HTTP.
6. **Correlation ID**: `TraceContextInterceptor` chỉ mở context cho RPC; `HttpExceptionFilter` gọi `getRequestContext()` (`packages/filters/http-exception.filter.ts` gần cuối) nhưng không có interceptor nào mở context cho luồng HTTP, nên `correlationId` luôn undefined trong lỗi HTTP. Nếu caller không gửi header `x-correlation-id`, service sinh UUID mới và trace bị đứt.
7. **Phụ thuộc DB chung**: `JwtAuthGuard`/`LogGateway` truy vấn bảng `users` do `user` service sở hữu; `test_`*/`request_logs` đồng bộ thủ công từ gateway (schema mirror local, commit "Sync local schema mirror"). Thay đổi schema ở service khác có thể làm vỡ âm thầm.

## Ghi chú / Cần xác minh

- **Guard toàn cục trên RPC**: `APP_GUARD` (`JwtAuthGuard`, `LanguageGuard`, `TokenBucketGuard`) dùng `switchToHttp().getRequest()`. Nếu Nest áp chúng cho handler microservice (hybrid app), mọi RPC sẽ lỗi vì `request.headers` undefined. Service đang chạy nên nhiều khả năng không áp; cần xác nhận bằng test e2e RMQ.
- **Cổng HTTP có expose ra ngoài không?** Mức độ TRD-01/02/13 là đầy đủ khi 8888/4001 truy cập được từ Internet; nếu chỉ nội bộ qua gateway thì giảm, nhưng RPC `redis.get`, `upload.delete` vẫn thiếu kiểm tra quyền.
- **Secrets**: `.env` nằm trong `.gitignore`, không được track (`git ls-files`); không thấy secret cứng trong `src/`. `scripts/seed-user.ts` chứa mật khẩu seed mặc định (`Admin@123456`...), chỉ nên chạy dev. `coverage-report.txt` được track (chưa kiểm tra nội dung).
- **Webhook / idempotency**: không có webhook. Email/upload không có idempotency key; khi chuyển sang manual ack/retry (TRD-08) message redelivery sẽ gửi email 2 lần hoặc upload 2 file.
- **FK** `notification.create`: `senderId`/`userId` không được kiểm tra tồn tại, vi phạm FK ra 500 (TRD-19).
- `test-scenario` **createMany race** (`test-scenario.service.ts:158-167`): dedupe theo method+path+name chỉ trong bộ nhớ, bảng không có unique index (`database/schema.ts:496-516`), nên hai lần gọi đồng thời tạo bản ghi trùng (Low, chưa liệt kê vào bảng).
- `expiryOf` (`test-auth.service.ts`): token sống dưới 60s luôn bị coi là hết hạn, login lại mỗi lần (không ảnh hưởng đúng đắn).
- Passport strategies (`packages/strategy/*`) và `jwt-sign.config.ts` hiện không được đăng ký trong module nào (code chết); giá trị fallback `dev-missing-google-client-*` sẽ không gây lỗi nếu sau này bật mà quên env.
